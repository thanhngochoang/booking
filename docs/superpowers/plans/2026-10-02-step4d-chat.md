**Goal:** A customer can ask a photographer questions before booking (at most 3 messages until the photographer answers, then free conversation), the same conversation becomes the booking's chat when the deposit is paid, both sides exchange text, photos and a one-time location with the booking pinned on top, propose and accept a new date once ("Đổi lịch"), and find every conversation from a list reachable from S01 and S14.

**Architecture:** One chat per (customer, photographer) pair, id `{customerId}_{photographerId}`, kind `inquiry` until a booking attaches (`kind: booking`, `bookingId` = the latest booking with that photographer). Clients **read** chats and messages through Firestore listeners and **write only their own read marker**; every message goes through the callable `sendMessage`, so the server enforces membership, the 3-message inquiry limit, the 7-day read-only window after a booking ends and the per-member unread counters. Business rules are pure TypeScript in `packages/domain` (`chat.ts`, use cases), Functions are thin adapters; a Firestore trigger on `bookings/{id}` attaches the chat and posts the system messages for status changes, so plan 4a's booking code is not edited. Rescheduling is a `system` message carrying a proposal; accepting it runs a booking transaction through 4a's `BookingStore` (new day must be free; old day freed) and marks the message answered. The app gets a `ChatRepository` port with a Firestore + Functions adapter and a fake, S11 (`/chat/:chatId`), the inquiry entry `/u/:uid/ask`, and the new list screen S68 (`/chats`).

**Tech Stack:** TypeScript (domain, Functions v2 `onCall`, `onDocumentWritten`), Firestore + Storage rules; Flutter, Riverpod 3, go_router, existing `MediaUploader` (plan 3c) and `LocationRepository` (plan 3a1).

## Decisions (where the spec is silent)

1. **Chat identity.** One chat per pair, id `{customerId}_{photographerId}` (both ids are opaque `[A-Za-z0-9_-]`, so `_` joins them unambiguously only together with the stored `customerId`/`photographerId`; never parse the id). A later booking with the same photographer re-points `bookingId` to the newer booking; earlier bookings keep `chatId` pointing to the same chat.
2. **Firestore shape.**
   - `chats/{chatId}`: `kind`, `customerId`, `photographerId`, `members: [customerId, photographerId]`, `bookingId?`, `photographerRepliedAt?`, `customerMessagesBeforeReply` (int), `lastMessageAt?`, `lastMessagePreview?` (≤ 80 characters; "Ảnh", "Vị trí" for media; system text for system), `lastSenderId?`, `readOnlyAt?` (booking closed + 7 days), `rescheduleUsed` (bool), `createdAt`, `updatedAt`.
   - `chats/{chatId}/members/{uid}`: `unreadCount`, `lastReadAt?` — the only document a client writes (its own: `unreadCount: 0`, `lastReadAt: request.time`).
   - `chats/{chatId}/messages/{messageId}` (ULID): `senderId?` (null for system), `type`, `body?` (text ≤ 2000 characters), `imagePath?` (storage key `chats/{chatId}/{uid}/{ulid}.webp`), `point?` (`GeoPoint`), `system?` (`{kind: 'booking_status' | 'reschedule_proposal', status?, proposal?: {day, start, end, byRole}, answer?: 'accepted' | 'declined' | 'expired', answeredBy?, answeredAt?}`), `clientId` (the sender's local id, for de-duplicating retries), `createdAt`.
3. **Closed inquiry** is computed, not stored: `kind == inquiry && lastMessageAt + 14 days < now`. The UI shows a line "Cuộc trò chuyện đã đóng. Gửi tin để mở lại."; sending reopens it (no server state to change).
4. **Read-only booking chat.** When the attached booking enters `declined`, `expired`, `cancelled`, `completed` or `reviewed`, the trigger sets `readOnlyAt = now + 7 days`; a new booking attaching clears it. `sendMessage` refuses after `readOnlyAt` with `not_eligible`.
5. **Retries.** `sendMessage` takes `clientId` (a ULID made on the device). If a message with that `clientId` already exists in the chat, it returns that message instead of writing a second one (store lookup by `clientId` inside the transaction: the message document id **is** the `clientId`, so a second create is detected by reading the document).
6. **System messages on booking status** (trigger): `requested` "Đã đặt cọc {amount}. Chờ {photographer} nhận trong 24 giờ.", `accepted` "{photographer} đã nhận buổi chụp.", `declined` "{photographer} đã từ chối: {reason}. Cọc được hoàn 100%.", `expired` "Yêu cầu đã hết hạn. Cọc được hoàn 100%.", `cancelled` "Buổi chụp đã huỷ.", `completed` "Buổi chụp đã hoàn thành." The text is rendered on the device from `system.status` and the booking (ARB strings), not stored, so wording can change.
7. **Reschedule.** Either party may propose on `accepted`/`upcoming` while `rescheduleUsed == false` and no proposal is pending; the **other** party answers (spec says the photographer accepts the customer's proposal; S09 shows "Đổi lịch" for both, so the counterpart accepts in both directions). Accepting: the new `day` must be free (`day_taken` otherwise), start must be a valid slot for the duration and in the future; old day freed, new day written with the booking's current day state (`booked`); booking `day/start/end` updated, `version + 1`, a `BookingEventRecord` with the booking's status and `actorId`; chat `rescheduleUsed = true`. A pending proposal expires when the booking leaves `accepted`/`upcoming` (trigger marks `answer: 'expired'`). The deposit and refund policy follow the new start (4a computes from `day/start`).
8. **"Xác nhận địa điểm"** sends a text message "Chốt địa điểm: {place}" prefilled from the booking's place (editable before sending). No new data.
9. **Chat list S68** (`/chats`) is a new screen: the spec needs an entry point ("cần danh sách hội thoại làm điểm vào từ S01") but gave it no code; per CLAUDE.md new screens take the next code, **S68**. Task 9 adds it to `screen_codes.dart`, the code table and a minimal mock section, and flags it to the user. Rows: avatar, name, last preview, time, unread badge, booking badge when attached; newest first.
10. **Entry points.** S01 header gains the chat icon (mock; was deferred by 3b4 "not built — no backend") with the total unread count; S14's chat icon (4c, behind the flag) opens S68; S09/S14/S19 "Nhắn tin" open `/chat/{chatId}`; S03 "Nhắn tin hỏi trước" opens `/u/:uid/ask`, which calls `openInquiry` and replaces itself with `/chat/{id}`.
11. **Images**: picked with `imagePickerProvider` (1 image), resized on device to ≤ 2048 px long side and encoded WebP quality 80 (use the image compression already used by plan 3c if any; else `package:image` is **not** added — reuse 3c's `PickedImage` pipeline and upload JPEG if WebP encoding is unavailable, ledger it), uploaded with `MediaUploader` to `chats/{chatId}/{uid}/{ulid}.webp`, then `sendMessage(type: image, imagePath)`. Storage rule: members only (checked with `firestore.get` on the chat).
12. **Location**: one-shot `LocationRepository.currentPosition()` (new method; medium accuracy, 10 s timeout) after asking permission on tap; message body empty, `point` set; bubble shows "Vị trí của {name}" with a map link (Google Maps `?q=lat,lng`).

## Review Focus

1. Customer sends a 4th inquiry message before any reply, possibly from two devices at once → exactly 3 stored, the 4th refused with `limit_exceeded` and the input explains why. Pinned by Task 2 ("the fourth customer message before a reply is refused, also when two arrive together").
2. The same message is retried after a timeout (the first actually landed) → one message, not two. Pinned by Task 2 ("a retried clientId returns the existing message").
3. Both parties tap accept on a reschedule proposal, or the booking is cancelled while a proposal is pending → the booking moves once or not at all; the proposal shows its final answer. Pinned by Task 3 ("the proposer cannot accept their own proposal", "a cancelled booking expires the pending proposal") and Task 3 ("accept twice applies once").
4. Booking ends → chat stays writable 7 days then read-only, and a new booking with the same photographer makes it writable again. Pinned by Task 4 ("closing a booking sets readOnlyAt; a new booking clears it").
5. Offline or a send failure → the bubble stays with "Gửi lại", nothing is lost when leaving and returning to S11 within the session. Pinned by Task 7 ("a failed send keeps the bubble with Gửi lại and retries with the same clientId").

`assertCanSend` (sample — the order matters):

```ts
export function assertCanSend(chat: Chat, senderId: string, now: Date): void {
  const role = roleInChat(chat, senderId);
  if (role === null) throw new DomainError('permission_denied');
  if (chat.readOnlyAt !== null && now.getTime() >= chat.readOnlyAt.getTime()) throw new DomainError('not_eligible');
  if (chat.kind === 'inquiry' && role === 'customer' && chat.photographerRepliedAt === null
      && chat.customerMessagesBeforeReply >= INQUIRY_MAX_UNANSWERED) {
    throw new DomainError('limit_exceeded');
  }
}
```
