## Decisions

1. **Recommender: keep `LocalRecommender` for phase 1; defer `services/recommender` and the `recommend` callable.** The service is a contract only (no code, no language; README proposes TypeScript). Its own README already says phase 1 needs no Cloud Run, only a `recommend` callable over a pure `packages/recommender-core`. That callable cannot be deployed on the Spark dev project, would add one invocation and an 800 ms deadline to every Home/Find page, and at ≤ 200 bookable providers ranks the same pool `LocalRecommender` already ranks on the device. The owner wants UI first. Wire it when one of these holds (written into the README in Task 8): more than 200 providers accept orders (the device pool is capped at 200, so ranking and search stop seeing everyone), the Find read cost passes $5/month (Chi phí Google), or a second client needs the ranking. `sendFeedback` stays a no-op until then.
2. **Find asks the server for bookable providers only.** `candidates()` queries `acceptingOrders == true` instead of `onboardingComplete == true`; the client filter from #133 stays as a guard. Docs written before #133 without the field are filled by the backfill CLI (Task 2), not by a client fallback in the query.
3. **The pool is cached on the device for 10 minutes** (`CachedPhotographerRepository`, single-flight, failures not cached). Find, its pages, filter changes, `similar` and S02.07 search share one read. A `not_accepting_orders` refusal in the booking flow clears it (Find has no pull-to-refresh and the mock adds none). Server checks (`ProviderOrderGate`) still guard bookings, so a 10-minute-old `acceptingOrders` cannot create a wrong booking.
4. **`stats.nextFreeDate` is event-driven plus one daily rollover**, not the hourly job of the 2026-09-30 spec: recomputed on every `availability/{uid}/days/{day}` write (bookings, events and "Đánh dấu nghỉ" all write there), when a profile becomes bookable, and at 00:10 Asia/Ho_Chi_Minh for every photographer whose stored date is before today. Fresher and ~24× fewer runs than hourly.
5. **"Free" day** = a day in `[today, today + 60)` with no `availability/{uid}/days/{day}` document. Any stored document blocks the day (`off`, `booked`, `pending`, and unknown states, which `FirestoreAvailabilityLookup` already treats as booked). No free day in 60 days → `nextFreeDate: null`.
6. **"Rảnh tuần này" queries `acceptingOrders == true`** (a closed provider cannot be booked from the shelf; spec silent, identity spec §4 spirit) and orders by `stats.nextFreeDate` then `stats.score desc` (#130's tomato/brick score, which replaced `stats.rating` in this query and its index before this plan in the waves; cross-plan review finding 35) then id. The writer of `nextFreeDate` also writes `stats.score: 0` when the field is missing, so a new photographer is never excluded by the `orderBy` (this is #130's invariant "`stats.score` is written whenever `stats.nextFreeDate` is"; this plan is that writer).
7. **Counters are recounts.** `likeCount`/`saveCount` = `count()` of `likes`/`saves` with that `postId`; `stats.completedCount` = `count()` of the photographer's bookings in `completed|reviewed`; `startingPrice` = min price of active services; catalog `serviceCount` = `count()` of active services in the specialty. Each recount runs in a transaction with the write (`tx.get(query.count())`, Admin SDK 13), and writes only when the value differs, so retries and re-fires are idempotent and races converge.
8. **`startingPrice` and `stats.completedCount` are added to this unit** although the issue names only `nextFreeDate`/`likeCount`/`saveCount`: no code writes them today, so every S02 card misses "từ 1,5M" and "112 buổi" (mock S02.01, S02.06), the budget filter keeps everyone and the price sort is random. Same trigger family, same tests.
9. **Explore tiles read one document `catalog/explore`** (`specialties.{code} = {serviceCount, coverUrl}`), maintained by `onServiceWrite`. `serviceCount` counts all active packages, including those of providers not yet accepting orders (cheap; see Needs the owner 1). The cover is the `coverUrl` of the most recently updated active package with a cover in that specialty (null → the tile's gradient placeholder). Only the Dịch vụ tab shows "n gói"; Địa điểm/Phong cách/Thợ ảnh tiles show the name over the placeholder (mock draws only Dịch vụ). A count of 0 hides the caption.
10. **Search (S02.07) runs on the device**: specialties, styles and areas by accent-folded substring (`foldVietnamese`), photographers by name from the cached pool (≥ 2 characters). No server index, no new reads when the pool is cached. Phase-1 limit: only bookable providers in the pool (≤ 200) are found by name; the server search is deferred with the recommender (Decision 1). A new screen, so Task 4 adds its mock frames and code first.
11. **The tomato display on S02 belongs to #130's data.** Task 7 implements only what #130 has not already shipped on S02 surfaces (home card meta, S02.02 meta, Find card meta, Find chip and sheet, "Rảnh tuần này" order), and is skipped (ledgered) if #130 is not merged.
12. **Mock deviations kept** (recorded in the ledger, not changed here): S02.01 chat icon shows a count (S07.02 caption allows it), `ReasonChips` under feed cards (spec 3e explainability), S02.02 share and `more_horiz` (need a share plugin and S20 report → Deferred), S02.04 category block below events (spec S02.04 "các khối Khám phá còn lại cuộn bên dưới"), S02.05 search and "Dùng vị trí của tôi" (earlier mock-parity ruling), S02.06 sort row and fallback note (§2 already notes them).
13. **Rollover schedule is a new Cloud Scheduler job** (`rollNextFreeDates`, daily): +$0.10/month (9th job: #129 added `paymentClock` as the 7th and #134's `createPayouts` lands earlier in the waves as the 8th; cross-plan review finding 37). Folding it into `pruneNotifications` (03:45) would leave yesterday's dates hiding everyone from "Rảnh tuần này" for almost four hours each morning.

1. **A booked day still shows "Rảnh T7 này".** A booking or a "Đánh dấu nghỉ" on the stored free day must move `nextFreeDate` to the next free day, and `pending` must block too.
