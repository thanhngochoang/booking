# Phase 1.5 · Staff money tools (#163) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Code goes to **booking-be**; each part's last task also updates docs in this repository. Each part is one unit: branch `plan/<issue>-<slug>` in both repos, booking-be PR lands first (`land.py <issue> --pr <n> --repo thanhngochoang/booking-be`), then the docs PR here.

**Goal:** Finance and admin staff work the money queues in the dashboard: approve, hold, resume and re-run payouts (S23.02); put unmatched bank transfers where they belong or send them back (S23.12); retry failed refunds, record refunds paid by hand and release money held by instant requests that found no photographer (S23.03); export the monthly tax report (S23.13). Every money operation of 10.000.000₫ or more needs a second person (S23.15).

**Architecture:** As in #162. Rules are pure functions in `packages/domain`; Cloud Functions callables are thin (`gate()` → domain use case); the dashboard reads Firestore with the Admin SDK through per-screen readers and writes only through callables. Money operations that start below the threshold run at once; at or above it they open a `staff_approvals` request. The two-person mechanism of #162 gains a second way to run an approved operation (`execute`, after the decide transaction, under a short claim) because these operations run through existing per-subject stores that cannot join the approvals transaction (decision D2).

**Tech Stack:** TypeScript (ESM, Node 24), `node:test` (domain, Functions unit), Cloud Functions v2 `onCall` (`asia-southeast1`), Firestore + Storage, Next.js 16 BFF (React 19, Vitest + RTL), Playwright on the emulators.

**Spec:** `docs/superpowers/specs/screens/staff-money.md` (M1–M5, §1–§12). Also `docs/superpowers/specs/2026-10-08-dashboard-web-design.md` (§2.3 readers, §2.4 writes, §4.2–§4.3 roles, §5.4 approvals) and `docs/superpowers/specs/2026-10-06-payments-payouts-design.md` (§3.3 mis-transfer table). Mock: `docs/design/dashboard-mock.html#S23.02`, `#S23.03`, `#S23.12`, `#S23.13`, `#S23.15`. #162 handover: `docs/superpowers/handover/ledger-162-dashboard-foundation.md` (its "Các ticket sau thêm gì" table and rulings 1–16 stand).

## Global Constraints

- Everything in #162's Global Constraints still holds (browser never touches Firestore/Storage; writes only through callables; TOTP on every staff route and callable; reasons 5–500 characters; no realtime listeners, queues refresh every 30 s; strings in `src/messages/vi.ts`; one primary action per screen; plain DTOs; Blaze switch; error codes in four places).
- **Roles:** every screen and callable here is `admin` and `finance` only (spec §0, §8). Sales and support get no menu item, a 403 page and `staff_forbidden` from the callables.
- **Threshold (M2):** an operation whose amount is **≥ 10.000.000₫** opens a second-approval request; below it runs at once. The value comes from `platform_config/money.twoPersonThreshold`, falling back to `DEFAULT_MONEY_CONTROLS.twoPersonThreshold = 10_000_000`. The approval `amount` is what the operation sends: the payout's `amountNet`, the refund's `amount`, the transfer's `amount`, the instant refund.
- **One person is enough (M3):** hold, resume, re-run a payout, re-send an existing refund, export the tax report.
- **No account or ID numbers on screen (M5):** DTOs, logs, audit `diff`, approval `params` and error messages carry at most the last 4 digits. The full ID number appears only inside the exported tax CSV.
- **No "edit amount" anywhere (M4).** Money changes only through the use cases named here.
- **New error code:** `already_paid` (assigning a transfer to a payment that is already paid or refunded). It needs rows in `packages/domain/src/errors.ts`, `firebase/functions/src/callables/errors.ts` `TRANSPORT_CODE` (`failed-precondition`), root `src/errors.ts` `HTTP_STATUS` (409), `firebase/functions/test/unit/errors.test.ts`, and `error.already_paid` in `apps/dashboard/src/messages/vi.ts`.
- **Late thresholds (spec):** payouts waiting for approval 24 h, on hold 72 h, processing 2 h; transfers 24 h; failed refunds 24 h; refunds pending 2 h; refunds awaiting an account 24 h; instant `no_match` 7 days.
- **Commits:** Conventional Commits, subject ends with `[#<issue of the part>]`, trailer `Co-Authored-By: TonyH <thanhngochoangbk@gmail.com>`. The booking-be PR body says `thanhngochoang/booking#<issue>`.

## Decisions this plan makes

Each goes into the part's handover ledger as a ruling.

- **D1 · Three units.** The spec's screens are independent apart from the shared money foundation, so they land as three units (table above). Part A carries every shared change.
- **D2 · Approved money operations run after the decide transaction, under a claim.** #162 runs an approved operation inside the approvals transaction (`run(tx, …)`). That fits operations whose store can share one Firestore transaction. The money operations here go through the existing subject stores: booking, ticket, verification, instant, group settlers and refund handlers. Each store builds its own transaction, so they cannot share one. `ApprovalKindSpec` therefore gets an optional `execute(approver, params, ref)`; a kind has exactly one of `run` or `execute`. For an `execute` kind, approving goes through three steps:
  1. **Claim.** One approvals transaction checks everything #162 checks (approve action, `same_person`, `pending`, expiry, `stillValid`). It then sets `claimedBy`/`claimedAt` and leaves the row `pending`. A claim younger than `APPROVAL_CLAIM_SECONDS = 120` makes a second decide or a cancel `conflict`.
  2. **Execute.** `execute` runs the operation with the approver as actor. Every operation is guarded by its entity's state (approve only `needs_approval`; resolve only an open review; mark manual only `failed`; cancel only `no_match`), so running it twice is `conflict`, not a second payment. If `execute` throws `DomainError` with a code in `STALE_CODES = ['conflict', 'not_found', 'not_eligible', 'already_paid']`, the outcome is stale. Any other error releases the claim in its own transaction and is rethrown; the row stays `pending` and can be approved again.
  3. **Close.** A second approvals transaction closes the row `approved`, or `rejected` with note `stale`. It writes `approval.decide` and clears the claim. If the row is no longer claimed by this caller, the call answers `conflict`.

  The money state is always the truth. The worst crash leaves a row `pending` whose operation already ran; the next approver's attempt is stale and closes it.
- **D3 · Audit.** Some operations' stores are written for this plan: payouts (`PayoutTx` gains `AuditWriter`), transfer reviews and refund operations. Those write their audit row in the same transaction. Operations that go through an existing subject store (assigning a transfer, marking a refund manual, staff-cancelling an instant request) write it right after commit through an `AuditLog` port, in its own transaction. Those entities also carry the decision on themselves (`review.decidedBy`, `manualBy`, the instant request's cancellation), so a lost audit write never loses who did what. A failed after-commit audit write is logged at error level with the entity id; the callable still returns the operation's result.
- **D4 · Payout fixes the spec needs.**
  - `holdPayout` accepts `pending` **and** `needs_approval` (the "Tạm giữ…" button sits on the Chờ duyệt tab). It still refuses `processing`, where money may be in flight.
  - A `failed` payout is final: its payments go back to payable and the next batch takes them. So "Chạy lại" on a failed payout is `staffExecutePayout`, which does three things in order:
    1. marks it `rerunAt`/`rerunBy`;
    2. creates the payee's new batches now (`createPayouts`);
    3. sends each new `pending` one.

    On a `pending` or `processing` payout it re-sends the same id (the gateway's idempotency key).
  - The Thất bại tab hides payouts that have `rerunAt`.
- **D5 · Permissions.** `payout.manage` is replaced by the 16 actions of spec §8. The CLI uses the specific actions.
- **D6 · No idempotency-key store.** Callables accept and ignore `idempotencyKey`. The entity state machines make a repeat `conflict`, and `DecisionDialog` already locks after the first confirm (#162 ruling 10).
- **D7 · Unmatched-transfer refunds** keep `Refund.paymentId` a required string. It is `''`, with the new `transferRecordId` set, instead of becoming optional across about 37 call sites. `isUnmatchedTransferRefund(r)` is the only test for it. These refunds use method `gateway` with `providerRef = txnId` and no destination (spec §4 "khi chưa có V2"). They write no ledger entry, because the money never entered the ledger. They are re-sent through a new `unmatched_transfer` refund handler.
- **D8 · Assigning a transfer reuses the subject settler.** `TransferNotification` gains `assignment?: {decidedBy, note}`. Every `SubjectSettler.settle` treats an existing record as a duplicate unless `reopensReview(seen, transfer)`, which is true only for an assignment on an open `needs_review` record. Assignment therefore runs exactly the automatic §3.3 rules and overwrites the record with its outcome and `review.resolution = 'assigned'`, atomically in the subject's own transaction.
- **D9 · Manual refunds keep `manual: true`.** `mergeRefundOutcome` currently forces `manual = false` on `done`. It changes to take `next.manual` on `done` and to carry `manualBy`, `manualPaidAt` and `manualNote`. Every existing caller already sends `manual: false` with `done`. The `refund_issued` ledger entry is written when a refund is created (`transferRefund`, `applyRefundToPayment`), so marking a refund manual adds no ledger entry.
- **D10 · Tax export.**
  - The full ID number exists only encrypted (`users/{uid}/private/identity.idNumberEnc`). Its only decrypt is the dev vault, because the production KMS vault is deferred. `exportTaxReport` therefore answers `not_eligible` wherever the dev vault is not allowed, exactly like the identity callables.
  - The screen's last 4 digits come from a new `idLast4` on the identity record (written at verification; missing → "—"). For studios and organizers they come from `verifications/{uid}.business.taxCode`.
  - The CSV goes to `exports/tax/{period}/{ulid}.csv`. The existing `pruneDataExports` already deletes everything under `exports/` after `EXPORT_TTL_DAYS = 7` (spec Q4), so no new job is needed.
  - The callable returns the signed URL itself. Spec §8's `tax_export` kind for `getSensitiveFileUrl` is not added (no screen re-downloads a file).
  - VAT and PIT are split from the payout's snapshotted `taxWithheld` in proportion to `DEFAULT_PAYOUT_POLICY.individualTaxBp` (500 : 200). The PIT part takes the rounding remainder.
- **D11 · Navigation.** The money group gets Chi trả, Chưa khớp, Hoàn tiền and Thuế. "Chờ duyệt" stays the single approvals entry from #162 (shared with #164), not a second "Duyệt lần hai" item. Sidebar counts come from the same reader as the S23.09 cards.
- **D12 · Tabs are URLs.** `?tab=<id>` is read on the server; a new `Tabs` component renders links with `role="tablist"`. A tab change is a navigation, so each tab is its own reader query and survives refresh.

## Review Focus

1. **The same person approving their own big operation, or two approvers at once.** A finance user proposes a 12.000.000₫ manual refund and then tries to approve it: `same_person`. Two admins press "Duyệt" together: one claims, the other gets `conflict`, and the refund is marked once. Pinned in A1 (`claim conflict`, `same_person`) and B6 (Playwright).
2. **Money that must not move twice.** Double-clicking "Gửi lại", re-running a failed payout the daily job already re-batched, assigning a transfer twice, approving a request whose payout was already approved through the CLI: each is one gateway call or a `conflict`/stale close. Pinned in A2 (`staffExecutePayout` after re-batch → not_eligible, no new payout), B2 (`assign twice → conflict`), B3 (`retryRefund twice → one gateway call`) and A1 (`execute throws conflict → rejected stale`).
3. **A full account or ID number leaking.** Payout and transfer DTOs, approval `params`, audit `diff`, CSV-less screens and error messages hold at most 4 digits. Pinned in A5 (`PayoutDetailDto has no account number`), B1 (`payer is masked on the record`) and C2 (`tax screen DTO has idLast4 only`).
4. **The threshold boundary.** 9.999.999₫ runs at once; 10.000.000₫ opens a request; a malformed `platform_config/money` falls back to the default instead of disabling the rule. Pinned in A1 (`requiresTwoPeople`, `moneyControlsOf`) and A5 (dialog label switches at the boundary).
5. **A tab that never empties.** A failed payout re-run by staff, a transfer resolved by someone else, a refund sent meanwhile: each disappears from its tab on the next refresh, and opening a stale row's action answers `conflict` with a message, not a crash. Pinned in A5 (Thất bại hides `rerunAt`), B5 and B6 (`conflict` shows `error.conflict`).
