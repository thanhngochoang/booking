## Decisions

1. **When an inquiry is closed** (the issue asks to define it): an `inquiry` chat is closed when `now ≥ (lastMessageAt ?? createdAt) + 14 days` (main spec §3b.1; `INQUIRY_CLOSE_DAYS`). A provider who stops accepting orders does **not** close inquiries (identity spec §4: "Bạn vẫn nhắn hỏi được"). Closed is derived, never stored: any message reopens it. The `createdAt` fallback covers an inquiry opened and never written to.
2. **Reopen gate:** a customer's message into a *closed* inquiry is refused with `not_eligible` when the photographer has `contactChannels.acceptInquiries == false` (reopening is a new inquiry). An open inquiry continues even after inquiries are turned off. The photographer can always reply/reopen. Closing does not reset the 3-message cap.
3. **A read-only booking chat becomes an inquiry again** when the customer taps "Nhắn tin hỏi trước" (`openInquiry`) after `readOnlyAt` has passed: `kind: inquiry`, `bookingId: null`, `bookingStatus: null`, `readOnlyAt: null`, keeping `photographerRepliedAt` (they have talked, so no 3-message cap). Without this, chat ids being `customer_photographer`, a past customer could never write again until a new deposit. Refused with `not_eligible` when inquiries are off. History stays in the same thread.
4. **The booking status is mirrored on the chat** (`chats/{id}.bookingStatus`, written by `syncBookingChat` on every status change of the attached booking, including `upcoming` and `reviewed`, which post no system message). The list reads it with zero extra reads. A chat document written before this plan has no field → no badge (dev data only; the next status change of its booking fills it).
5. **The S07.02 badge uses the booking status label** (`BookingStatusX.label`, e.g. "Đã nhận", "Sắp tới", "Hoàn thành"), not the hard-coded "Đã đặt". The mock contradicts itself (S07.01 shows "Đã nhận" for the same booking that S07.02 labels "Đã đặt"); the spec says "badge trạng thái". Task 7 changes the mock's S07.02 badge to "Đã nhận" and the spec sentence.
6. **Retry never re-uploads a stored image.** `storage.rules` forbid overwriting `chats/…` objects, so sending is split into `uploadChatImage` (returns the path) and `sendImagePath`; the controller remembers the uploaded path per `clientId` and a retry only calls `sendImagePath`. Within one screen session only (a restart drops pending bubbles, as today).
7. **Image path extension `.jpg`** (content type `image/jpeg`; today's `.webp` name with a JPEG body is wrong). Stored messages keep their paths. The server also checks `parts[1] === chatId` so a message cannot point at another chat's file.
8. **Download URLs are resolved once per app run** through `mediaUrlResolverProvider` (`chatImageUrlProvider`, kept alive after success, retried after an error). The sender's own just-sent photo keeps showing from the local file (no flash of an empty bubble when the message lands).
9. **Unread counts:** one query listener on `chats` plus one listener per `chats/{id}/members/{uid}` (≤ 50), replacing a `get` of every member doc on every snapshot, run twice (list + total). `totalUnreadProvider` sums `myChatsProvider`. Reading a chat now updates the list badge (only the member doc changes on `markRead`, which the old code never saw).
10. **Chats without any message are hidden from S07.02** (`lastMessageAt == null`): a customer who opened "Nhắn tin hỏi trước" and left without writing must not leave a blank row in the photographer's list.
11. **Empty preview of a booking chat** (last message is a status system message, `previewOf` returns `''`) shows the `chatSys*` text of `bookingStatus`; the own last message gets the prefix "Bạn: " (mock).
12. **`…` in S07.01** shows when it has at least one item: booking chat → "Xem buổi chụp" (existing); inquiry seen by the customer → "Xem hồ sơ". The report item (S20, #144) will make it always present like the mock.
13. **`/chats` stays outside the tab shell** (mock S07.02 draws the tab bar): it is opened from S02.01 and S05.01 (two tabs) and from push links `/chats`; moving it under one branch would switch tabs. Recorded as a mock deviation.
14. **Compression 1280 px q75 without EXIF** (issue and cost spec §11) supersedes the screen spec's "≤ 2048px (WebP)"; Task 7 updates `booking.md`. It is #147's compressor; this plan only calls it (Task 6).
